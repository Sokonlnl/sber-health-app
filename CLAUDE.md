# Health Monitor iOS: правила проекта

Тестовое задание: два экрана мобильного приложения для мониторинга здоровья на SwiftUI:
главный экран и экран одного показателя (давление).

Источники правды (читай перед работой, не переспрашивай то, что там записано):
- `docs/BRIEF.md`: задача и критерии приёмки.
- `docs/DESIGN.md`: токены, экраны, состояния, взаимодействия.
- **Эталон дизайна: Figma**, главный экран `63:25250` (с 18.11; прежний `47:2127`):
  https://www.figma.com/design/wiH1VTFFlY0KXC1M6RQ8Fx/?node-id=63-25250
  Снимок: `docs/design/home-figma-63-25250.png`. Figma главнее холста; при расхождении правится код, а не Figma.
  Читать через Figma MCP (`get_design_context` по узлу), не по памяти.
- Дизайн-холст (Claude Design, экран давления и шторка до появления их версии в Figma): https://claude.ai/artifact/HE2nEUW27e5hrek5bLxKE3

## Стек
- Swift 5.10+, SwiftUI, iOS 17+, Swift Charts.
- Архитектура: MVVM, модели состояния через `@Observable`.
- `HealthMonitor.xcodeproj` и общая схема `HealthMonitor` хранятся в Git. CI и локальная проверка используют этот проект.
- Линтер: SwiftLint (`.swiftlint.yml`). Форматирование: swift-format.
- Тесты: Swift Testing / XCTest. UI-тесты делают скриншоты.

## Структура
```
HealthMonitor/
  App/              точка входа, навигация
  DesignSystem/     Colors, Typography, Spacing, Radius, компоненты (ui)
  Features/
    Home/           главный экран (View + ViewModel)
    Pressure/       экран давления, шторка добавления
  Domain/           модели, зоны давления, агрегация по периодам
  Data/             моковые данные и репозиторий
HealthMonitorTests/
HealthMonitorUITests/
docs/               BRIEF, DESIGN, HARNESS, QA-LOG, design/ (эталонные скриншоты)
.claude/agents/     роли агентов
```

## Жёсткие правила
1. **Только токены.** Цвета, шрифты, отступы и радиусы берутся из `DesignSystem/`. Хардкод `Color(red:)`, `.font(.system(size:))`, числовых отступов во View запрещён.
2. **Сначала ищи, потом создавай.** Перед новым View проверь `DesignSystem/` и `Features/`. Если подходящий компонент есть, используй его. Если нет, создай в `DesignSystem/` с `#Preview` для каждого состояния, и только потом применяй.
3. **Логика не живёт во View.** Зоны давления, агрегация, форматирование: в `Domain/` и ViewModel, с unit-тестами.
4. **Обязательные состояния:** loading, empty, error, нормальное. Для каждого экрана и карточки.
5. **Доступность:** Dynamic Type, подписи VoiceOver у иконок и графиков, цель нажатия не меньше 44×44 pt, контраст текста не ниже 4.5:1.
6. **Медицинская осторожность.** Это справочная информация. Не давать диагнозов. Зоны давления: Норма (<130 и <85), Повышенное (130–139 или 85–89), Высокое (≥140 или ≥90).
7. **Данные пока моковые.** Один источник в `Data/`, без сети.

## Рабочий процесс (агенты)
Работаем ролями, каждая в `.claude/agents/`:
- `swiftui-builder`: собирает экран по `DESIGN.md`.
- `design-system-keeper`: следит, чтобы не появлялись дубли компонентов и хардкод.
- `design-reviewer`: сравнивает скриншот с эталоном из `docs/design/`, возвращает отчёт.
- `qa-agent`: тесты, линтер, логи CI, запись в `docs/QA-LOG.md`.

Цикл: builder собирает → CI собирает и снимает скриншоты → reviewer и qa проверяют →
builder исправляет → повторяем, пока отчёты не станут пустыми.
Каждый найденный и исправленный дефект записывается в `docs/QA-LOG.md`.

## Окружение
Два режима, определи по `uname`/наличию `xcodebuild`:
- **macOS (основной для дизайн-ревью).** Быстрый цикл локально: `scripts/local-verify.sh` (SwiftLint --strict,
  сборка, установка в запущенный симулятор, скриншоты всех экранов в `build/local/<время>/`), `--tests` добавляет unit-тесты.
  design-reviewer сравнивает эти скриншоты с `docs/design/home-figma-63-25250.png`. Ошибки компилятора видны сразу —
  не пушь, пока локальная сборка красная. CI остаётся финальной проверкой перед «готово» (UI-тесты, аудит, видео).
- **Windows (Xcode нет).** Сборка и тесты только в GitHub Actions на macOS (`.github/workflows/ci.yml`). Результаты смотри через
  `gh run view --log-failed` и `gh run download`.
В обоих режимах: не утверждай, что код собирается, пока сборка (локальная или CI) не зелёная.
Текущее состояние работы и следующие шаги: `docs/HANDOFF.md`.

## Git
- Ветка `main`, небольшие осмысленные коммиты.
- Формат: `тип(область): описание`, типы `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`.
- Папка `docs/design/references/` в `.gitignore`: скриншоты сторонних приложений не публикуем.

## Автоматические проверки (не ждать просьбы)
Основная сессия обязана сама запускать проверяющих агентов, пользователь их не вызывает:
1. После каждой работы `swiftui-builder`: сразу `design-system-keeper`. Найденные нарушения возвращаются builder.
2. После каждого завершённого запуска CI: `qa-agent` (логи, тесты, запись в `docs/QA-LOG.md`).
3. После запуска CI со скриншотами: `design-reviewer` сравнивает их с `docs/design/` и `docs/DESIGN.md`.
4. Коммит и пуш Swift-кода без шага 1 запрещён. Результаты проверок кратко показываются пользователю.

Пункты 1 и 4 принудительные: хук `.claude/hooks/commit-gate.mjs` блокирует `git commit`, если Swift-файлы менялись
после последнего запуска keeper или содержат хардкод. Хук `swift-tokens-lint.mjs` проверяет каждый правленый
Swift-файл сразу после правки. Обходить хуки нельзя: исправляй причину. Подробности в `docs/HARNESS.md`, раздел 4.

## Верификация (навык `/verify`, `.claude/skills/verify/SKILL.md`)
Готово = есть доказательства. Перед словом «готово» пройди `/verify`: чек-лист по diff (`node scripts/checklist.mjs`),
keeper, коммит, CI, `node scripts/ci-summary.mjs`, просмотр скриншотов, qa-agent и design-reviewer, итог «проверено / не проверено».
1. **Три красных раунда CI подряд по одной задаче: стоп**, отчёт пользователю, решение за человеком.
2. **Нестабильные тесты** не перезапускать до зелёного, не обходить `sleep`, не отключать. Чинить причину или удалить с записью в QA-LOG.
3. **Изменение не меняет свои проверки.** Эталоны snapshot, `waivers` аудита доступности, `.swiftlint.yml`, хуки,
   `.claude/settings.json`, определения агентов меняются только отдельным коммитом и с одобрения человека
   (правила `ask` в настройках, CI-страж `Guard checks`). Новые эталоны принимаются только скриптом
   `scripts/accept-snapshots.mjs`, который не перезаписывает существующие.
4. **Ревью привязано к содержимому.** Отметка keeper хранит хеш Swift-файлов; любая правка после проверки требует новой.
   Отчёт design-reviewer указывает запуск CI и коммит; отчёт по старому коммиту недействителен.
5. **Коммит говорит, как он проверен:** трейлер `Verified-by: keeper, checklist C01 C05; CI <id|pending>`.
   Режим ворот: `COMMIT_GATE_MODE` в `.claude/settings.json` (`off`, `observe`, `enforce`).
6. **Уроки → правила.** Каждый исправленный дефект превращается в тест, хук или пункт `docs/CHECKLIST.md`.
7. **Уборка.** Раз в итерацию удалять устаревшие пункты чек-листа, правила и тесты, которые больше ничего не ловят.

Визуальные изменения экранов ловят snapshot-тесты (`HealthMonitorTests/__Snapshots__/`). Эталон обновляется
только при намеренном изменении дизайна: удалить PNG, прогнать CI, просмотреть новый кадр, закоммитить.
